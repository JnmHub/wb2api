## Confirmed findings and changes

- **P1, settings lost updates:** replicas previously read and replaced the whole
  settings document under separate process-local locks. API keys and unrelated
  settings could overwrite one another. PostgreSQL mutations now lock, load the
  latest row, call the mutation once and commit in a single transaction. Startup
  seed uses insert-if-absent, rejects malformed/unreadable files and never
  silently overwrites a concurrent winner. Local refresh uses compare-and-swap
  so an older read cannot replace a newly committed cache snapshot. Partial
  prompt edits also merge inside that transaction rather than from a stale cache.
- **P1, revoked panel sessions:** a delayed access-time touch could upsert a
  revoked session back into PostgreSQL. Touch now only updates an existing,
  unexpired row and rejects a session when that row no longer exists. Panel
  sessions use PostgreSQL when configured, otherwise the file backend; Redis
  is not a panel-session backend. First-time file migration serializes the
  marker check and import, preventing a delayed importer from resurrecting a
  session revoked after another replica finished importing it.
- **P1, account state across replicas:** management changes were not routinely
  reloaded by peer pools, and full-record saves could overwrite unrelated fields
  or recreate deleted records. The account persistence changes add shared-state
  reconciliation and conflict-aware saves. Fresh explicit imports remain
  replacement operations; stale background saves do not become fresh imports.
  Unchanged authoritative credits preserve local consumption estimates during
  polling. Strict seed loading aborts on unreadable/malformed sources without
  consuming its one-time marker; an absent directory is a supported fresh-install
  case that also leaves the marker unset for a later real source.
- **P1, local slot race:** selection and the in-flight increment were separate.
  Dispatch now atomically reserves a slot and releases it after the attempt.
  Local-only and pinned routes honor the bounded wait; shared-gate rejection
  releases any local reservation.
  Feedback-based sticky escape remains a preference: a sole slow but healthy
  account is eligible when there is no alternative.
- **P1, stalled error bodies:** an upstream non-200 body could hold its account
  slot indefinitely after the response-header deadline. Error reads now have a
  time bound; closing an incomplete custom wire body closes the socket before
  the HTTP body can try to drain it.
- **P2, expired Redis slots:** streams longer than the lease could disappear from
  shared concurrency accounting. Held slots now renew until release. Renewal
  never recreates a lost member. This remains a best-effort distributed lease:
  a Redis outage longer than its TTL cannot guarantee a strict global cap.
  Queue deadlines now bound Redis I/O as well as polling sleeps. Heartbeats use
  short operation deadlines; release can still wait up to 2 s for an outstanding
  heartbeat plus up to 2 s for cleanup when Redis is unresponsive, since socket
  reads are not interrupted instantly by context cancellation.
- **P2, false stream success and health feedback:** read failures and upstream
  SSE error envelopes no longer emit Chat `[DONE]`; nonstream client cancellation
  is reported as client-aborted, not as an upstream failure. Chat preserves
  buffered partial output and emits a sanitized error; Responses uses a sequenced
  error instead of a fabricated completed response. Anthropic recognizes both
  object and scalar error envelopes, terminates immediately, and does not emit
  `message_stop` after failure. Aggregate errors and follow-up failures use stable
  public messages rather than upstream body/error details. Responses follow-up
  rounds close their own bodies and reset the idle-cancel target to the current round.
- **Benchmark correctness:** Chat TTFT previously accepted matching JSON keys in
  empty deltas. It now requires semantic content, reasoning or tool-call output.
  Historical benchmark numbers using different detectors are not a controlled
  baseline for these measurements.

## Deployment limitations

Every replica must use the fixed writer protocol. Old binaries during a rolling
upgrade can still perform stale replacements. Back up first and avoid mixed
writers. Shared settings and account snapshots converge on their refresh
intervals, not at the exact instant another replica commits. Whole-document
settings Save and fresh account imports intentionally retain replacement
semantics. A successful fix does not reconstruct historical secrets.

## Latency evidence

The earlier standalone, direct-replica and Caddy runs differed in concurrency,
topology and upstream. Their p50/p99 values do not measure Caddy overhead and
cannot establish why a particular production request took seconds.

The isolated review stack used one mock (200 output tokens at 50 TPS), the same
load-generator implementation, 200 requests and concurrency 100 per measurement.
Each path below was measured **once inside the Docker network**:

| Client destination | Success | TTFT p50 | TTFT p99 |
| --- | --- | --- | --- |
| Mock directly | 200/200 | 0.707 ms | 32.241 ms |
| One gateway directly | 200/200 | 4.702 ms | 61.349 ms |
| Caddy → one gateway | 200/200 | 7.630 ms | 43.625 ms |
| Caddy → two gateways | 200/200 | 5.125 ms | 51.584 ms |

This supports millisecond-scale gateway/proxy overhead in this synthetic local
setup. It is not a production upstream benchmark, a saturation test or a
statistically significant ranking of one versus two gateways. The earlier HA
p50 of ~2.46 s was not reproduced here.

Separate Windows-host-to-published-port measurements were run twice at c100.
The first round's p50 was 3.881 ms for mock, 8.393 ms for direct gateway,
26.651 ms for single Caddy and 16.504 ms for HA Caddy; p99 was ~1.9–2.0 s even
for the mock alone. The reversed-order repeat varied substantially (mock p50
305.229 ms, direct 223.939 ms, single Caddy 11.060 ms, HA 37.566 ms). Removing
the host path also changed the client runtime/placement; host forwarding and
scheduling are plausible contributors, not individually proven causes. The
measurements were not on an otherwise idle dedicated benchmark machine.
Do not attribute the historical long tail to Caddy or claim a measured speedup
against the earlier unmatched results.

For production attribution, collect client start, gateway dispatch, upstream
headers and first semantic-output timestamps on the same request. Raw synthetic
results remain in the private local temporary benchmark directory.

## Live cross-replica management verification

On the isolated two-replica review stack (not production):

- A login on replica 1 authenticated on replica 2; logout on replica 2 revoked
  access on both.
- 20 simultaneous key creations alternating replicas, plus an unrelated setting
  update, retained all 20 new keys and the original key. Both views converged
  within 625 ms after the writes completed.
- Disabling/changing a synthetic account on one replica appeared on the peer
  within 317 ms; the test restored that account afterward.
- A soft-deleted test key appeared deleted on the peer within 634 ms.

The final binary was then deployed to both isolated replicas and the checks
repeated: 20 additional concurrent keys plus an unrelated settings change
preserved all 21 prior entries (including the soft-deleted entry); convergence
was 649 ms. Account changes converged in 1406 ms and a deleted key in 635 ms.
Cross-replica login and revocation passed again. No production data was touched.
A final Docker-internal HA smoke run on that binary completed 200/200 at c100:
TTFT p50 6.191 ms, p99 620.953 ms, max 621.059 ms, total 9.457 s. Its higher tail
than the first run illustrates run-to-run variability; it is not evidence of a
measured speedup or of the cause of the historical production delay.
These are end-to-end regression checks, not recovery of the reported lost data.
