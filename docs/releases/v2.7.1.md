# v2.7.1 — 模型 id 用错了字段：DeepSeek 在目录里却调不了

v2.6.0 起 `/v1/models` 发布的华为模型名字是**显示名**（`DeepSeek-V4.1-Flash`），
而聊天接口只认**内置清单的 `model_id`**（`deepseek-v4.1-flash`）。于是目录里
看得见的模型，点进去就是：

```
TM.000010051  您当前无权调用该模型，请联系企业管理员开通。
```

这条报错极容易被读成「账号没买」，实际是**我们把模型名发错了**。

## 证据（同一账号，直连上游）

| 发的模型名 | 结果 |
| --- | --- |
| `deepseek-v4.1-flash` | HTTP 200，正常出字 |
| `DeepSeek-V4.1-Flash` | `TM.000010051 无权调用` |
| `deepseek-v4.1-flash-1017` | HTTP 200 |
| `DeepSeek-V4.1-Flash-1017` | `TM.000010051` |
| `glm-5.3` / `kimi-k3` / `openpangu-2.1-pro` | 通过模型校验（下游报并发上限，说明名字对了） |
| `GLM-5.3` / `Kimi-K3` / `OpenPangu-2.1-Pro` | `TM.000010051` |

结论：每个模型**只有一个可调用拼写**。内置清单里 `model_id` 是小写 id、`model_name`
是展示名，只有 id 能用；只有 agent-center 那批（`GLM-5.2`）用展示名。

## 根因

两处叠加：

1. `fetchBuiltinModels` 存 `Name: id`，丢掉了展示名
2. `MergeModels` 用 `strings.ToLower(ID)` 做键：agent 源的 `DeepSeek-V4.1-Flash`
   与内置源的 `deepseek-v4.1-flash` 撞在同一个键上，最后**谁 richer 谁留**，
   结果留下的是展示名那个。

## 修复

- **内置源优先**：`sets` 顺序改为 builtin → agent → benefit，碰撞时第一个源拥有
  wire 拼写（`model_id` 才是可调用名）
- **保留展示名**：`Name` 存 `model_name`，用于第二个合并键与别名翻译
- **按展示名去重**：`GLM-5.2-ArkTS-SPARK` 与 `glm-5.2-sft-harmony` 是同一个模型，
  `智速模式` 与 `speed` 也是 —— 目录从 14 条收敛到 12 条，顺带消掉那条乱码条目
- **展示名自动翻译**：客户端仍可用 `DeepSeek-V4.1-Flash` 请求，网关按目录把它
  翻成 `deepseek-v4.1-flash` 再发；翻译发生在**选号之前**，这样模型冷却的键
  也统一成 wire id（否则两种拼写各自一套冷却，互相绕过）
- **报错不再含糊**：流内 `error_code` 信封解析出业务码后直接给客户端
  （`upstream: 您当前无权调用该模型… (TM.000010051)`），并把该模型在该账号上
  停 30 分钟，下次自动换号

## 实测（2.7.1，全部走网关）

| 模型 | 结果 |
| --- | --- |
| `deepseek-v4.1-flash` | OK「在线」 |
| `DeepSeek-V4.1-Flash`（别名） | OK「在线」，响应里 model 归一为 wire id |
| `deepseek-v4.1-flash-1017` | OK |
| `kimi-k3` / `kimi-k3.1-pro` | OK |
| `glm-5.3` / `openpangu-2.1-pro` / `openpangu-2.0-flash` | OK |
| `GLM-5.2`（agent 源，仍是展示名） | OK |

12 个模型全部可调用。

## 升级说明

- 升级后先点一次「重新发现模型」，旧目录里的展示名会换成 wire id
- 客户端如果写死了旧展示名（`DeepSeek-V4.1-Flash`）也能继续用：网关会翻译
- 注意 `max_tokens` 太小时，纯推理模型会只产出 `reasoning_content`、没有正文，
  网关会回 `upstream returned reasoning without content`，把预算调到 200 以上即可
