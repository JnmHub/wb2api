# v2.9.1 — 流内失败也带 request_id 与 request_shape

v2.9.0 只补好了「普通错误分支」。流式请求失败时代码走的是另一条路
（`pipeStream`），那里既没有 id 也没有结构摘要——报告里那条
`upstream_aborted / 502` 的记录就是空的。

## 之前漏在哪

```go
// v2.9.0 的 stream.go
UpstreamCode: upstreamCodeOf([]byte(errText(streamErr))), RequestID: requestIDOf(r)
```

- `requestIDOf(r)` 从 context 读 id，但**没人往 context 里写过**，永远是空串
- `Shape` 根本没传进来

## 现在

- 请求 ID 在**写出第一个响应字节之前**就绑到 context 上，并同步设置
  `X-Request-Id` 响应头（流式与非流式都一样）
- 出站结构摘要（`request_shape`）随 context 一起走，流式、非流式、完成、失败、
  客户端中断五种记录都能拿到
- `emitWithLatency` 统一兜底：事件里没填的 id / shape 从 context 补
- 流内错误帧本身也带上 `request_id` 和 `upstream_code`，客户端在 SSE 里就能看到

于是任何一条记录都能对上客户端手里的 id：

```text
HTTP/1.1 200 OK
X-Request-Id: 01a1ee6c409579debf30ab5455ddffd5

... data: {"error":{"message":"upstream: The request param is invalid … (InferHub.001001005.400)",
                     "type":"server_error","request_id":"01a1ee6c…","upstream_code":"InferHub.001001005.400"}}
```

用量库里同一行：

```json
{"at":"19:19:50.512","model":"deepseek-v4.1-flash","outcome":"upstream_aborted","status":502,
 "error":"upstream InferHub.001001005.400",
 "request_id":"01a1ee6c409579debf30ab5455ddffd5",
 "request_shape":{"bytes":812,"messages":3,"tools":1,"has_tool_choice":true,"tool_choice_kind":"auto","stream":true}}
```

## 面板能查了

请求列表接口（`GET /api/v2/usage/recent`）现在把 `request_id`、`upstream_code`、
`request_shape` 提到顶层字段，拿客户端报的 id 直接搜即可。

## 测试

```
ok  gateway/openai  TestCodeArtsStreamErrorKeepsDiagnostics
                    两帧 SSE（正常内容 + error_code 帧）→ HTTP 200、
                    X-Request-Id 非空、事件 id 与头一致、shape 非空且 tool_names_over_64=1
ok  gateway/openai  既有 CodeArts / Stream / Latency 用例全过
ok  api             EventFromGateway 保留业务码与 shape
```

## 仍未确认

- 这条路径只能证明**失败发生在流内**，不能指出被拒的具体字段；新记录第一次出现时，
  `request_shape` 会告诉我们当时带了什么（工具数、是否 tool_choice、超长名个数、字节数）
- 19:19:50 那条记录产生在 v2.9.0 上，补不回 id 与 shape
