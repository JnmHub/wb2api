# v2.10.0 — 对照参考实现补三处华为渠道缺漏

拿 `ProvidersPlugin/Agent2Providers` 的 `codearts/` 模块逐文件对了一遍，找出三处**真实缺漏**，
其中第一处很可能就是你们那批 `TM.00001050` 的成因之一。

## 1. 对话请求缺三个模型头（`chat.rs` 的 `HeaderProfile::headers`）

参考实现写得很明确：**上游把模型名也当请求头，`model-id` / `model-name` / `x-model-id`
三个键都要，少一个都不行**。我们一个都没发，只在 body 里带 `model`。

现在补齐整组头：

```http
Content-Type: application/json
Accept: text/event-stream
client_version: Vscode_<plugin-version>
Agent-Type: ChatAgent
X-Language: zh-cn
is_confidential: false
plugin-name: …
plugin-version: …
model-id: deepseek-v4.1-flash
model-name: deepseek-v4.1-flash
x-model-id: deepseek-v4.1-flash
x-auth-token: <STS>
x-snap-traceid: …
app-id: CodeAgent3.0
user-session-id: …            (有租约时)
maas_type: benefit            (福利模型)
```

值用的是**wire 名**（目录里的 `model_id`），不是客户端传的展示名——`DeepSeek-V4.1-Flash`
会先被翻译成 `deepseek-v4.1-flash`，四个地方（body + 三个头）保持一致。
签名覆盖所有头发出的那串字节，所以顺序是先定模型名、再签名、最后发。

真机实测：`GLM-5.2` 与 `deepseek-v4.1-flash` 带新头都正常返回「在线」。

## 2. 上游错误体里的凭据未脱敏（`redact.rs`）

上游偶尔会把被拒的请求回显在错误体里（签名错时回 AK、token 错时回 STS）。我们把这段
原文截断后塞进了客户端响应和用量记录——一处回显就等于把凭据交给所有能看日志的人。

现在按参考实现的三个拼法（原文 / URL 转义 / JSON 转义）逐条遮盖：

```
bad signature for [redacted] with token [redacted]
```

不碰正文结构，只盖凭据值。

## 3. APIG 级拒绝被当成「客户端参数错」

`TM.*` / `APIG.*` 是**网关层**的拒绝，请求根本没到模型：

| 码 | 含义 | 来源 |
| --- | --- | --- |
| `TM.00001001` | 请求体不是合法 JSON（比如把压缩过的体直接发） | 参考实现注释 |
| `TM.00001041` | 会话并发上限（每账号 3 路） | 实测 |
| `TM.00001050` | 网关拒绝该请求 | 你们这次的报错 |
| `TM.00001051` | 该账号无权调用该模型 | 实测 |
| `APIG.0301` | 凭据解不开 | 你们之前那次 |
| `APIG.0602` | 凭据过期 | 实测 |

以前这些（除 0001051）会走到通用分支，而通用分支对 400 的处理是「客户端的问题」。
现在 APIG 级拒绝一律记为**账号侧短暂状态**：冷却该账号 30 秒并换号，不再把责任推给调用方。

## 附：我把能想到的请求形状都打了一遍上游

同一账号、`deepseek-v4.1-flash`、带租约逐条发：

| 请求 | 结果 |
| --- | --- |
| 9 条消息 + 40 个工具（约 45KB，与你们这次的摘要接近） | **200** |
| 单条 200KB 消息 | **200** |
| 200 个工具 | **200** |
| 复用同一个 `chat_id` 连发两次 | **200** |
| 带未知字段 `foo` | **200**（上游直接忽略） |
| `temperature=5.0` | `InferHub.001001005` |
| `top_p=9` | `InferHub.001001005` |
| `n=3` | `InferHub.001001005` |
| `max_tokens=-1` | `InferHub.001001005` |
| `tool_choice` 指向未声明的工具 | `InferHub.001001005` |
| `messages: []` | `InferHub.001001009`（「chat messages is required」） |

结论：**`TM.00001050` 不是请求形状问题**——体积、工具数量、未知字段、`chat_id` 复用都能过。
它更像账号或模型在该时刻的状态（额度/风控/网关策略），这也支持上面第 3 条的改法。
