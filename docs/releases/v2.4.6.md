# v2.4.6 — 额度耗尽不再被当成 60 秒限流

发布日期：2026-10-29

## 修了什么

### 1. 429 `14018`（额度已用尽）现在按「额度耗尽」处理

以前一个已经没额度的账号，被上游回 `429 {"error":{"data":{"code":14018,…"额度已用尽"}}}`
时会被当成**普通限流**：给这个模型挂 60 秒冷却，60 秒后账号又回到「可用」，下一个
请求再撞一次、再挂 60 秒，无限循环。面板上它永远是「可用」，客户每次都要多付一次
上游往返。

现在这类 429 直接 park 整个账号到**次日 04:00**（与 402 同一条路径），面板显示
「冷却中」，选择器不再派单，客户不会撞到它。

### 2. `code` 解析支持嵌套结构

上游把 `code` 放在不止一个位置：顶层、`error.code`、`error.data.code`、`data.code`。
旧实现只读顶层，嵌套 body 下所有 code 判定（`6004` 窗口额度、`14003` 频率限制、
`11140` 风控、`14018` 额度耗尽）全部失效，只能退化到文本匹配。

现在按固定顺序查找（顶层 → `error` → `data` → `body` → `detail` → `response` →
其余键按字典序，深度上限 4），结果不依赖 Go 的 map 迭代顺序。

### 3. 面板把「冷却」与「模型冷却」拆开

以前点「冷却」筛选时，后端把**账号级冷却**和**有模型在冷却**的账号做了并集，
于是 60 秒的模型窗口也会被算进「冷却」：测试账号后数字猛涨，一分钟后又自己掉回去，
和顶部「冷却中」卡片对不上。

现在：

| 位置 | 含义 |
|---|---|
| 冷却（筛选条 + 卡片） | `State()==cooling`，账号级：`cooldown/breaker/degrade/balance` 任一在未来 |
| 模型冷却（新增筛选条 + 原有卡片） | 该账号有模型处于 per-model 窗口，账号整体仍可用 |

`/api/v2/accounts/summary` 里 `cooling_total` 现在只数账号级冷却，`model_cooling`
单独数模型窗口。

## 不变的行为

- 普通 429（没有额度措辞、没有 reset 时间）仍然只给该模型挂 60 秒窗口，不 park 账号；
- 402 仍然 park 到次日 04:00；403 `11140` 仍然只给该账号打 2 小时风控标记；
- 额度耗尽不写 `credit=0`，账号在 04:00 或手动「清除冷却」后重新可用；
- 风控连坐暂停仍默认关闭（`WB_RESTRICTION_HOLD_SECONDS=0`）。

## 已知边界

- per-model 冷却窗口仍是每个副本进程内的内存状态，多副本之间不共享：A 副本已经
  把某账号某模型挂起，B 副本仍会再撞一次。想彻底消除需要把模型窗口放进 Redis。
- 后台不做主动探测：账号只有在被真实请求（或手动「测试账号」）打到之后才会更新状态。

## 升级

```
git fetch --tags && git checkout v2.4.6
docker compose up -d --build
```

不需要迁移数据，不需要清 Redis/SQLite。面板上如果之前习惯用「冷却」筛选看模型窗口，
请改用新增的「模型冷却」。
