# v2.9.0 — 001001005 可定位了；工具名改写补齐 tool_choice 与历史

两件事一起发的：让 `InferHub.001001005.400` 这类失败**查得到**，同时修掉一个自己造成的
同类失败。

## 1. 失败记录能对应到客户端那一次请求

以前一笔 400 在用量库里只有 `Bad Request` 四个字：`EventFromGateway` 写的是
`http.StatusText(ev.Status)`，上游业务码在 `finishError` 里被丢掉了。截图里那个
`InferHub.001001005.400` 因此无法与任何一条记录对应。

现在每次请求都有网关自己的 id，客户端能拿到，库里也存：

**客户端可见**

```http
HTTP/1.1 400 Bad Request
X-Request-Id: 5f1c9e0a-…

{"error":{
  "message":"upstream 400: The request param is invalid, Please check it (InferHub.001001005.400)",
  "type":"invalid_request_error",
  "request_id":"5f1c9e0a-…",
  "upstream_code":"InferHub.001001005.400"
}}
```

**库里的记录**

| 字段 | 内容 |
| --- | --- |
| `error` | `upstream InferHub.001001005.400`（不再是 `Bad Request`） |
| `Extra.request_id` | 与客户端拿到的 id 相同 |
| `Extra.upstream_code` | 业务码 |
| `Extra.request_shape` | `{bytes, messages, tools, has_tool_choice, tool_choice_kind, stream, max_tokens, tool_names_over_64}` |

`request_shape` 只记**结构**：字节数、消息条数、工具个数、有没有 `tool_choice` 及其类型、
是否流式、输出预算、超长工具名个数。**不记**正文、工具参数值、请求头、凭据。

流式路径同样填这两项：流内错误帧（HTTP 200 + `error_code`）的失败也带 `upstream_code`。

## 2. 工具名改写补齐 `tool_choice` 与消息历史

`PrepareBody` 只改写了 `tools[].function.name`，没改引用同名工具的两处：

- `tool_choice`（字符串形式 `"<原来的长名字>"` 或 `{"type":"function","function":{"name":…}}`）
- 历史消息里的 `messages[].tool_calls[].function.name`

结果就是「声明里是 64 字符的短名，选择里还是 65 字符的原名」——上游对不上，回
`InferHub.001001005`。现在三处一起改，响应侧照旧还原成客户端的原名。

顺带修掉一个更隐蔽的：改名前只克隆了外层对象，`function` 子对象仍是**请求体里那一份**，
改写会污染 `q.shaped`，导致同一次请求的下一个换号尝试拿到已经变短的名字和过期的映射表。
现在连 `function` 一起深拷贝。

## 3. 丢掉上游明确不接受的参数组合

同一个 `001001005` 还会由下面几种组合触发，现在在出站前丢弃：

| 组合 | 原因 |
| --- | --- |
| `max_tokens` + `max_completion_tokens` 同时出现 | 两个输出预算，上游只认一个（保留 `max_tokens`） |
| `n > 1` | 只产出一个 choice |
| `stream_options` | 流式是网关强制的，`include_usage` 由网关自己处理 |

其余字段**原样转发**：宁可让上游明确拒绝并留下诊断记录，也不静默改客户端要的值。
