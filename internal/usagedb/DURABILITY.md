# Usage durability contract

## Acceptance and integration

`Record(Event) error` now commits a local SQLite WAL outbox with `synchronous=FULL` before success. It does not wait for the remote PostgreSQL sink. Call it after response output, not on the first-token path. Existing calls that ignore returns compile but must be migrated: success is the acceptance boundary, any error must be surfaced/alerted. A local commit error can be ambiguous: do not blindly resubmit with a new identity. Reopen replays whatever actually committed. Real durability still depends on the filesystem/device honoring fsync.

PostgreSQL requires `Options.OutboxPath`, a stable writable **local persistent volume per replica**. SQLite defaults to `<database-path>.outbox.db`. Preserve the database, WAL, and stable path across process/container restarts. No shared/network-filesystem outbox, symlink aliases, copying a running outbox to a second writer, restoring an old outbox snapshot, or manually deleting receipts. OS-exclusive ownership locks reject ordinary concurrent openers. An outbox is bound to a random sink ledger identity; destination changes fail instead of silently replaying into a different ledger.

`Ready() error` and `Health() Health` expose local durability failure/capacity so the gateway can reject new paid work. They read an immutable atomic snapshot without SQL or the local admission mutex: prior response-completion fsyncs do not move onto the next request's readiness path. Startup publishes before returning DB; accepted admission, acknowledgement, local failure and Close publish after their complete state transitions. Concurrent reads can observe the previous snapshot while a transition is still in progress; an already-published local failure/Close never becomes ready again in that DB instance. Sink delivery error is a separate atomic diagnostic, not a globally atomic combined health snapshot. Remote delivery failure is reported separately and still permits local durable recording while capacity remains. **Readiness is a preflight, not a capacity reservation.** Concurrent completions or disk exhaustion can still make Record fail after paid work. This does not guarantee exactly-once accounting for upstream work accepted before a crash and before Record succeeds, nor enforce hard cluster quotas with an asynchronous sink. Ordinary quota queries see delivered sink data, not undelivered local pending events. `DayIncludingPending(start)` provides consistent sink-plus-this-replica-pending counters for Today startup; it returns errors rather than pretending an unreadable sink is zero and cannot see other replicas' undelivered outboxes.

## Bounds and pressure

- `QueueSize` is now a **request-detail shedding threshold**, not accounting capacity. `OverflowDrop` / `OverflowSample` never sample accepted accounting facts. `Dropped` counts omitted details (and rejected calls after Close), not lost accepted quota values; Written and Dropped are no longer complementary.
- `OutboxMaxBytes` defaults to 256 MiB of pending serialized payload. This is a logical budget, **not** a strict physical file-size limit: SQLite indexes/page overhead, WAL and freelist high-water add disk usage. Deleted pages are reused; operators must budget/monitor the actual filesystem. Full budget returns `ErrOutboxFull` without accepting that event. Drain frees capacity.
- `MaxEventBytes` defaults to 256 KiB. Oversized/malformed optional diagnostics are omitted while retaining accounting. Oversized accounting dimensions return `ErrEventTooLarge`, non-finite credit / NUL accounting dimensions return validation errors. Local storage I/O errors latch admission closed until reopen; queue full or bad input does not globally latch.
- Record uses a dedicated local group committer, separate from remote delivery: greedily batch already-queued events into one FULL-WAL transaction, without intentional batching delay, at most 256 events / 4 MiB of encoded variants (one singleton may exceed this up to `2*MaxEventBytes`). Every successful caller is acknowledged only after commit succeeds. Commit failure is ambiguous for the whole written group, latches local durability, and returns errors; no caller-side automatic retry with a new identity.
- Local admission queue capacity is 64 events, each retaining full/minimal encoded variants, at most `128*MaxEventBytes` (32 MiB by default), plus the active 4 MiB batch or singleton exception, one carry event, one gate-serialized encoder/enqueue waiter (each at most `2*MaxEventBytes`), bounded JSON/SQL scratch and caller-owned arguments. This is not a 4 MiB queue claim; configuration controls the bound. No unbounded retained retry queue exists.
- Admission encoding runs under a separate context-aware semaphore, never under the fsync mutex. Gate/channel waits use WriteTimeout (default 10s); expiry returns transient `ErrAdmissionBusy`, meaning not accepted and not a sticky storage failure. After enqueue, a caller waits for its definitive commit/error result, not a timeout that abandons an ongoing commit. Per-group SQL work also uses WriteTimeout. CPU encoding, scheduling and OS fsync are not hard-real-time bounded; Record is not wait-free.
- Replay loads at most 256 events, stopping at approximately 4 MiB serialized payload plus one event. `Workers` remains for source compatibility but is effectively 1: ordered replay is required by the compact receipt protocol. Sink history/facts intentionally grow with retained accounting history; no automatic history retention is implemented.

## Replay and idempotency

Every persisted event has stable `(random source ID, monotonically increasing AUTOINCREMENT sequence)` identity. One source is strictly ordered. A sink transaction writes never-sampled accounting facts, daily/hourly aggregates and optional request details, and advances `usage_sources.seq` atomically. Failed or uncertain commits replay the same events; already committed sequences are skipped. Outbox rows delete **only after confirmed sink commit**. Crashes around acknowledgement/deletion cannot double-count an accepted event. Receipt storage is one row per outbox source, not one row per event; there is no per-event receipt cleanup window. Source rows must outlive every possible replay/backup of that source. They may accumulate if operators repeatedly create new outboxes. `usage_batches` remains only as an unused legacy schema table; old rows are not needed by the new protocol.

PostgreSQL's existing cross-replica transaction advisory lock remains; import/rebuild transactions take the same lock. PostgreSQL replay batches bulk-insert facts/details and preaggregate daily/hourly dimensions, then sort unique rollup keys and bulk upsert. Each bounded batch uses at most four data INSERT statements instead of four per event, plus constant receipt/lock/transaction overhead; 256 events remain below the 65,535-parameter limit. SQLite retains the per-event prepared path. The global lock still serializes sink transactions: this change reduces lock-held remote round trips rather than claiming unlimited cross-replica scaling.

## Rebuild and migration

`usage_facts` is a never-sampled immutable accounting ledger excluding request diagnostics. Exact-range Totals/Group, pair estimates and CreditSince read facts; Recent alone reads sampled requests. Daily/hourly quota sums always include all delivered accepted events. Existing legacy details seed facts at upgrade. Original daily/hourly tables are snapshotted as `legacy_daily` / `legacy_hourly`; `RebuildRollups(ctx)` adds only post-upgrade facts to those immutable snapshots, preserving historical aggregate-only contributions rather than erasing them. Cannot reconstruct historical timestamps/details that were already lost before this change. Do not rebuild manually from requests or mutate facts/baselines externally.

Legacy JSONL/complete-detail old SQLite imports remain resumable and now write facts alongside rollups in the same import transaction. New-version SQLite ledgers and old aggregate-only SQLite sources use an **offline one-time atomic full snapshot** instead: stop the source gateway, drain its durable outbox, then import. Source outbox ownership is locked; nonempty outboxes are refused. Retained details and all accounting facts copy independently. Whole source daily/hourly sums are added to both target live totals and immutable rebuild baselines; imported facts are marked legacy so rebuild cannot double-count. No subtraction or inference from sampled details is used. A SHA256 receipt across all copied tables commits in the same destination transaction: unchanged retries no-op, changed sources refuse (this is a final migration cutoff, not ongoing replication). Existing nonzero partial row-import cursors require reconciliation before switching to full snapshot, rather than risking duplicates. Snapshots use bounded per-row streaming but one potentially large transaction; large databases need a maintenance window and disk/WAL planning. A new-version source's configured outbox path is persisted in its SQLite meta, and changing that path requires explicit migration. Concurrent old path imports/old-version source writers are unsupported; the source must remain stopped. Do not run old-version writers against the migrated sink: they do not create accounting facts and would invalidate rebuild assumptions.

PostgreSQL counters/durations widen to BIGINT in a one-time transactional migration; old large tables may require a maintenance window for schema locks/table rewrite. Backup and rehearse upgrades. Startup still requires the sink available for schema/migration and ledger identity; reopening with the remote sink entirely offline is not implemented.

## Shutdown and validation

`Flush() error` first waits on a FIFO local admission barrier (reporting sticky local storage failure), then drains a sink snapshot through the last accepted sequence; it does not wait forever for later producers. A sink failure returns an error with durable pending work retained. `Close() error` starts its CloseTimeout budget before fencing admission, immediately closes a separate admission signal so blocked producers wake, drains/resolves all previously enqueued local callers, then attempts final sink drain. Timeout cancels local/sink DB work, but the worker still resolves every queued acknowledgement before handles close. Close closes handles and releases source ownership. Repeated Close returns the same result. Failed Close does not erase pending disk records. Close cannot promise an OS/device-level wall-clock deadline and can wait for caller-owned `SQL()` connections.

Focused `go test ./internal/usagedb` covers trigger-injected sink failure/recovery, local persistence failure latch, snapshot/reopen replay, lost commit acknowledgement state, high-water AUTOINCREMENT after empty outbox, budget rejection, ownership exclusion, concurrent Record/Close, cancellation, sampled-detail full quota sums, poisoned diagnostics and lossless aggregate-baseline rebuild. Actual child-process kill tests additionally verify accepted local replay and committed-but-unacknowledged replay with per-event distinct values, source ownership release, and repeated restart, on Windows and Linux (including Linux race). Optional real PostgreSQL tests run only with an externally provisioned isolated `WB_TEST_POSTGRES_DSN`: receipt replay/reopen, sampled/aggregate-only SQLite snapshot import and rebuild, and full 256-event bulk-vs-SQLite comparison across all rollup measures/dimensions. This is not real power-loss/device-failure, PostgreSQL process-crash/network-failover or production-load evidence.
